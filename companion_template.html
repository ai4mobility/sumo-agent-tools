Building SUMO Tools for AI Agents

An AI model can read SUMO's manual. It cannot know that a speed means nothing on an empty road, what counts as a queue, or that one simulation run is not evidence. You know these things. This page shows where that knowledge goes inside a tool, and what it changes, measured on a real network around USF.

The part of the tool only you can write

In the traffic flow class you wrote Python functions that drive SUMO through TraCI. An AI agent can call the same functions as tools. But the model never reads your code. It reads a name, a description, the inputs it may fill in, and the text that comes back. Everything it knows about traffic has to be in those words.

The rule of this page. Every sentence in a tool description is a claim. We test each claim against a real SUMO run. The toolkit makes {{D.claims_n}} claims; {{D.claims_pass}} pass (tab 9).

2 · A queue needs a definition

Ask three tools for "the queue" and you can get three numbers, because each uses a different definition:

  • Halting vehicles (getLastStepHaltingNumber): vehicles slower than 0.1 m/s on one lane, right now.
  • SUMO's lane-area (E2) detector (getJamLengthMeters): vehicles slower than 5 km/h (1.39 m/s) and within 10 m of the next one form a jam; the length counts the gaps. It sees only the stretch the detector covers.
  • The engineer's back of queue: the last slow vehicle still joined to the stop line, wherever it is. Timing studies report it per cycle (often the 95th percentile), because the queue grows on red and empties on green.

Try it: Fowler WB at 30th St, at {{e2b.snap_t|0}} s (the longest queue of the hour)

Every vehicle counts, including the ones that never got in

In a cell transmission model, vehicles are conserved by construction: what enters a cell either stays or leaves. SUMO keeps two side doors open. A tool that forgets them reports the wrong delay, and the error grows exactly when the network is in trouble.

The script picks cycles of {{D.raw_cyc_min|0}} to {{D.raw_cyc_max|0}} seconds, greens as short as 4 s and 4-second yellows. With short cycles, cars wait less at each red, and delay falls by {{D.raw_cut|0}}%. But the script knows nothing about people on foot. To cross the widest legs of Fowler (94 ft curb to curb in this network) a pedestrian needs a 7-s walk plus 94 ÷ 3.5 = 27 s of clearance, 34 s in all; at Bull Run Dr the plan leaves 4. Its 4-second yellows are also shorter than the ITE change interval for 45–50 mph approaches.

Going deeper: why the same seeds help (optional)

A seed fixes SUMO's random draws: driver imperfection, departure lanes, speed factors. With the same seed, both plans see the same drivers, so the difference between the runs is mostly the plan. Statisticians call this common random numbers. The confidence interval for the mean paired difference is d̄ ± t₀.₉₇₅,ₙ₋₁ · s / √n, with s the standard deviation of the n paired differences. FHWA's microsimulation guidance asks for multiple runs for the same reason. Your inference course covers the rest.

Calibrate before you compare

Every plan comparison above assumed the simulated traffic looks like the real traffic. Checking that is calibration, and it is the step an agent is most tempted to skip.

The check: GEH

GEH = √( 2 (M − C)² / (M + C) )
Msimulated hourly count at a station (veh/h) Cfield count at the same station and hour (veh/h) targetGEH < 5 at 85% of stations or more (FHWA Traffic Analysis Toolbox, Vol. III, 2004)

In words: the miss, scaled so that a big station and a small one are judged fairly. Simulating 2,100 veh/h where the counter saw 2,000 gives GEH 2.2, a pass. Simulating 300 where it saw 200, the same miss of 100, gives GEH 6.3, a fail.

What one corridor call returns

[[TXT_CORRIDOR]]
Five habits of a lean SUMO tool.
  1. Take names people use (cross streets, EB/WB, mph), and turn them into SUMO IDs inside the tool.
  2. Answer the engineer's question in one call (an approach, a corridor, a comparison), not one lane at a time.
  3. Return a few labelled numbers with units, never raw XML.
  4. Measure, don't compute from spot readings: travel time from vehicles that drove the corridor, like Bluetooth or probe data.
  5. Return errors as plain sentences the model can act on ("needs at least 34 s"), never a stack trace.

Seven questions every SUMO tool description must answer

  1. What does it return, in what units? mph, ft, veh/h, s/veh; "as of the last step".
  2. When is the answer undefined or partial? No vehicles; a queue longer than the detector; unfinished trips.
  3. Which definition does it use? Halting, jam, back of queue; space-mean or time-mean speed.
  4. Does it change the simulation, or let time pass? Read-only, acts now, acts at the next phase, runs forward (relative or absolute).
  5. What will it refuse, and why? The rule and its source (MUTCD, ITE, your agency).
  6. How much evidence is behind it? One snapshot, one cycle, one run, ten seeds; calibrated or not.
  7. Who must approve before the result is used? And how the result is labelled as AI-assisted.

Seven decisions turned the first into the second

  1. Start from the engineer's question, not the API function. One question needs four primitives: the signal string, the next switch, the clock, and the network's connections.
  2. Take inputs the way people name things. Cross streets go in; sumolib finds the id inside the tool.
  3. Translate codes and units. Each letter becomes a movement (from the network's connections) and words a driver would understand (from SUMO's table of signal states); the clock time of the next switch becomes a countdown.
  4. Write the result for a reader who cannot see SUMO, with the warm-up or after-peak warning outside 900–4,500 s.
  5. Write the description: what it does, the input with an example, what each word in the result means, units, that it only reads, its caveats, and the tool to use instead for the whole cycle.
  6. Write the input rules (the schema): one text input, described with an example.
  7. Test every claim. The example checks five, and GitHub runs it with every change to the repository.

Writing the description

Answer the seven questions at the end of tab 9. Three habits help:

  • Write only what you test. A sentence the tests do not check is a guess, and the model will treat it as a fact.
  • Spend words on knowledge, not politeness. get_approach_state's description is the longest in the toolkit ({{D.words_approach}} words) because it carries the queue rule, the spillback flag and the warnings; list_intersections needs {{D.words_list}}.
  • Use the names engineers use: cross streets, EB/WB/NB/SB, mph, ft, veh/mi/lane. Never make the model handle SUMO ids.

Writing the result

You can read bare values because the context is in your head: you wrote the call, you know the units, and you know what time it is in the simulation. The model has only the text. Description or result? Rules that never change (the queue definition, the 85% flag, input units) go in the description. Anything that depends on the state of the simulation (the clock, an empty block, a teleport, a failure) can only go in the result, because only the result knows the state.
Text or JSON? Either works, if it explains itself. A result such as {"back_of_queue_ft": 274, "verdict": "no spillback", "period": "after peak"} carries the same knowledge. The toolkit returns short sentences because they read like a briefing.
Evidence, not decisions. "Advance to a time between 900 and 4,500 s" helps the model get good evidence. "Retime this signal" is the engineer's call, and does not belong in a result.
A good result is not a guarantee. In run G the model read the AFTER-PEAK WARNING, mentioned it, and answered anyway. The harness and the engineer still check the evidence.

  3. Add a @claim test for each sentence of the description to test_claims.py, and run it.
  4. Try it by hand, with a small model on your laptop (walkthrough/qwen_harness.py: put the tool in MENU and your question in QUESTION), or in Claude Code, which gets every tool through mcp_server.py.

Ideas for your first tool

  • Worst queue during the analysis hour: read the back of queue at the end of every red; report the worst and when.
  • Level of service for an approach: control delay over the hour, the HCM level, and the vehicles and seeds behind it.
  • Travel-time reliability: median and 95th-percentile corridor travel time from the vehicles that drove it, with how many trips.
  • An incident: close a lane for a period; report the change in queue and travel time against the same seeds without it.
  • Detector health: compare a detector's counts with the field counts at its station, and say whether to trust it.

The traffic knowledge is the hard part of each one. The Python is the easy part.

Fit card, lever card, and check yourself

Fit card · Wrapping a traffic simulator as tools for an AI agent
Idea in one sentence
Give the model a short menu of simulator functions, each with a description that says what it returns, in what units, when the answer is undefined, and what it refuses.
Why it works
The model knows a tool only through its words and its results. Tested words turn guesses into checked steps; rules in the body hold even when the model ignores the words.
Fits these tasks
Repeated simulation studies (signal retiming, work-zone and incident what-ifs), TMC questions about the current state, calibration bookkeeping. Leverage labels: retrieval (reading the simulation), prediction (the simulator predicts; the agent asks), judgment stays with the engineer.
Needs this data
A network whose geometry an engineer has checked; counts at stations (the agency's count program); timing plans; the agency's timing standards.
Breaks when
Descriptions promise what was never tested; the network is not calibrated; one run stands in for evidence; the question needs a judgment no tool can check (is two seconds of delay worth a longer wait for pedestrians?).
Keep the classical method when
The study is one fixed sequence that never changes: a plain script (a workflow) is cheaper, faster and exactly repeatable. Required procedures with fixed steps (HCM analyses, warrant studies) stay procedures.
Transportation lever · Tool design for simulation agents
What the general method assumes
Descriptions taken from the API docs are enough, and the model will use the tools sensibly.
What transportation already knows
Theory: q = k·v, conservation, queues and shockwaves. Agency experience: MUTCD pedestrian timing, ITE yellow, FHWA calibration targets, multiple runs. Data: count programs, timing sheets, probe travel times.
Where it enters
Tools: names, units, definitions, rules in the body; checks and people: calibration sign-off; context: short engineer-shaped results.
How we'd show it helps
Same model, same task, API-shaped tools as the baseline: count wrong conclusions, invalid plans, calls and tokens over several runs. A natural extension of Lab 1.
When it could hurt
Rules stricter than the agency's block good plans (some agencies allow a 4-s walk); long descriptions cost tokens on every call (tab 8); a prior can be wrong, so test it (tab 6).

Check yourself

1. An agent reports "Fowler WB is moving at {{e1.naive_mean_mph|0}} mph" from a lane-speed tool. What do you check first, and what would you change in the tool?
Show an answer
Check how many vehicles were on the lanes. If many lanes were empty, the {{e1.naive_mean_mph|0}} mph is mostly speed limits. Change the tool to average the vehicles' speeds, report "no vehicles" when there are none, and report vehicles and stopped vehicles beside the speed (tab 3).
2. A teammate's tool returns mean delay from the trip file. At 1.4 times the demand, delay rises from {{D.naive10|0}} to {{D.naive14|0}} s/veh. Is the network coping?
Show an answer
You can't tell from that number. It averages finished trips only. Counting everyone due to start, delay went from {{D.eng10|0}} to {{D.eng14|0}} s/veh, with {{D.unf14|,0}} trips unfinished. Ask the tool for the ledger (tab 4).
3. An agent says Webster's plan cut delay by {{D.raw_cut|0}}% in one run. Name three things you check before showing it to a signal engineer.
Show an answer
(1) Timing minimums: pedestrian walk + clearance, minimum greens, ITE yellows. (2) Evidence: several seeds, paired, with a confidence interval. (3) Calibration: was the demand checked against counts and signed off? Here the first check alone cut the gain to {{D.chk_cut|0}}% (tab 5).
4. Your calibration passes GEH at 15 of 16 stations. The agent asks to start comparing plans. What should happen next, and who does it?
Show an answer
An engineer reviews the worst stations (is the one failure explainable?) and the network, then signs off. The agent cannot approve its own calibration; in the toolkit, approval is a command for people, not a tool (tab 6).
5. A classmate's queue tool returns {"q": {{D.q_m|1}}, "s": 0}. Rewrite it as a result a model can use without seeing SUMO.
Show an answer
Name each number and give units, state the verdict either way, and say when the reading cannot answer the question. The toolkit's version of one such reading: "[[RES_QUEUE]]; [[RES_SPEED]] space-mean speed ... [[RES_VERDICT]] (the flag is set at 85%)", followed by an AFTER-PEAK WARNING because it was read at {{D.raw_time|,0}} s (tab 10).
6. Lever question. Pick one tool your capstone agent will need. Which definition, unit or rule from traffic engineering would you write into it, and how would you test that it helps?
Show one way to answer
Example: a dashcam damage tool should state the minimum crack width it detects and its units, and refuse frames with no GPS fix. Test: run the same agent task with and without those lines in the description and the check in the body, over several runs, and count wrong reports.
